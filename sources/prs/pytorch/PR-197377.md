Summary:

`zero_` on CUDA was moved off the `fill_` kernel and onto `cudaMemsetAsync` in
#195303 (`df69a036b4c2`, "[ATen] Zero CUDA tensors with cudaMemsetAsync instead
of a fill kernel"), which added `zero_cuda_` and repointed the `CUDA` dispatch
key for `zero_` in `native_functions.yaml`. On affected ROCm versions that path
silently returns wrong data: `hipMemsetAsync` captured into a HIP graph leaves
stale bytes behind, so a buffer `zero_` reports as zeroed reads back non-zero.
No error, no NaN, correct shape and dtype, so nothing downstream notices.

This is a ROCm runtime regression, not a PyTorch one, and it is bounded:

| ROCm  | memset under graph capture |
|---|---|
| 6.4.2 | clean |
| 7.0.0 | broken |
| 7.1.0 | clean |

The fix landed in ROCm/clr `3038c4c3777eeb55eabfddee56807c6f74b1b77c`, and
pdesupinski confirmed the bug does not reproduce on 7.1.0. So the window is
`[7.0.0, 7.1.0)`: `zero_cuda_` takes the memset fast path everywhere else, and
inside the window falls back to `self.fill_(0)` -- what `zero_` did before
#195303. CUDA is untouched.
