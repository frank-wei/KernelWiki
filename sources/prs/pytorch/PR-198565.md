Summary:
D120460087 reverted `zero_cuda_` to the `fill_` kernel for ROCm [7.0.0,
7.1.0) because `hipMemsetAsync` recorded into a HIP graph leaves stale
bytes (ROCm runtime bug, fixed in ROCm/clr 3038c4c3 and clean on 7.1.0).
That blanket revert also degrades every NON-capturing workload: an A/A
serving comparison on MI350X (same model, same host, good = pre-guard
build vs bad = post-guard build) shows `aten::zero_` switching from ~181
driver memsets to ~145 single-block `FillFunctor` kernel launches per
forward, and the resulting launch/contention storm inflates every kernel
on the box by 15-75% at identical grids — GPU time per forward 53ms ->
75ms (+42%), a direct serving QPS regression on the rocm70 fleet. Full
trace analysis: P2519416887.

The corruption requires an ACTIVE stream capture; outside capture the
memset is sound. So gate the fallback on capture status instead of
reverting wholesale: on ROCm 7.0.x, `zero_cuda_` takes the memset fast
path when `at::cuda::currentStreamCaptureStatus()` is `None` and falls
back to `fill_(0)` only while capturing. Same pattern as the capture
check in `Copy.cu`; `currentStreamCaptureStatus()` is context-safe (no
