The previous FlexGEMM integration carried a second QuACK runtime stack inside PyTorch: `gemm_act`,
configuration mirrors, callback registries, template heuristics, and a long operation-specific vendoring
series. Feature work had to cross two implementations, and QuACK could not own configuration legality,
compilation, caching, or launch.

Route the QUACK backend through QuACK's modern EpiMod frontend while keeping captured FX as the
expression IR. PyTorch owns graph semantics, output planning, allocation, and graph-level fallbacks
(`torch/_inductor/kernel/flex_gemm/`: `fx_cutedsl_codegen.py` plans QuACK-owned stores and emits a TensorSSA
EpiMod source; `lowering.py`, `template.py`, `runtime.py` render and call it). The concrete FlexGEMM
EpiOps are PyTorch-owned too (`quack_ops/`: `GroupedMainStore` and the grouped local reductions subclass
