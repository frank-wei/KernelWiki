`range` (RangeFactories.cpp:156) and `arange` (RangeFactoriesKernel.cpp:23) already widen the step via `at::acc_type`, and CPU `logspace` computes its step and `pow` in double. CPU `linspace`, and CUDA `linspace` and `logspace`, kept everything in `scalar_t`, so for half and bfloat16 the step was rounded to the output dtype before being multiplied by the index, and CUDA `logspace` also evaluated `pow` in half. For `linspace(0, 10, 38)` element 3, CPU returned 0.810546875 where the correctly rounded half value is 0.811035156.

The step type was written with integer range in mind (See #27957: "step should be of double type for all integral types"), and #43578 later added bfloat16 by editing only the dispatch macro line. Delete `NOTE [Linspace+Logspace precision override]` in `test_tensor_creation_ops.py` that recorded "our Linspace and logspace torch.half CUDA kernels are not very precise", but #31962, which introduced it, only checked that the output matched PyTorch 1.2.0 and pinned the measured error as a 0.0039 tolerance without root-causing it.
