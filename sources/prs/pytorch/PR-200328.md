## Summary

radixSelect finds the k-th value for topk, kthvalue, median and nanmedian. Its ROCm version re-reads the slice (from global memory, or from its 3 KB shared-memory cache once the candidates fit) on every 2-bit radix pass, and spends two barriers per pass combining per-warp counts, so the single-block kernels are dominated by its serial latency.

This keeps slices of up to REGS_MAX_E x blockDim elements in registers for the whole selection, loaded and converted once (REGS_MAX_E is 20 on GFX9 and 14 elsewhere, which keeps wave32 kernels at 16 waves per SIMD). 1-byte types off GFX9 keep the general path, which was faster for them on gfx1100. For k <= 16 from either end, a pre-pass bounds the answer with the per-wave maxima and ranks the few candidates directly, falling back to the radix walk when too many keys tie. On GFX9 the per-pass count combine uses one barrier with DPP adds; other targets keep the two-barrier combine, which is cheaper there with 32 warps per block. The general path, still used for 8-byte types and longer slices, also gets cheaper. Only ROCm code in SortingRadixSelect.cuh changes.
