**Summary.** `define_user_defined_triton_kernel` always wrote a user-defined `triton.jit` kernel as an `async_compile.triton('''<source>''')` string, even when `defines_triton_kernels_as_code()` is on, and the per-def `re.sub` rename used for generated kernels only made def names unique. That left the string form impossible to delete, and once a user kernel's closure (helper defs, globals like `SCALE`, aliased imports like `from triton.language.math import abs as op`) is spliced into the wrapper's one namespace, two kernels from different files would silently share whichever binding came last, giving wrong numbers. The user-kernel path now builds the same source in both modes and, when kernels are code, hands it to `emit_triton_kernel_definition`, whose rename is replaced by `_rename_kernel_module_globals`, which uses `ast` to suffix every top-level def, assignment and post-def import with the kernel name.
