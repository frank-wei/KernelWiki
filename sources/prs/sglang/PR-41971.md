## Motivation

<!-- Describe the purpose and goals of this pull request. -->

On gfx950, the wo_a batched gemm always launches with one fixed kernel config. That config was tuned for small M (M <= 64), so it gets slow as M grows.

With dspark (currently 5 draft tokens), each request verifies 5 + 1 tokens, so `M = num_reqs * 6`. Once a batch has more than 10 requests, M goes past 64 and we hit this slow path.

## Modifications

<!-- Detail the changes made in this pull request. -->

- Add a tile table, `_TILE_BY_MAX_M`, and pick the single-launch tile `(BLOCK_M, BLOCK_N, BLOCK_K, num_warps)` by M:
  - M <= 64: 16 x 32 x 512, 2 warps (unchanged)
  - M <= 128: 64 x 32 x 256, 4 warps
  - M <= 256: 64 x 64 x 256, 4 warps
  - otherwise: 64 x 64 x 128, 4 warps
- `BLOCK_N` stays a multiple of 32, as the fp8 grid epilogue needs.
- Add a test that checks every new tile gives exactly the same output (bit for bit) as the original 16-row t
