## Motivation

On Ascend NPU, Qwen3-VL workloads with variable prompt and image lengths can trigger repeated Triton compilation during prefill.

The NPU preparation path calls:

```text
get_cos_sin_with_position
  -> apply_interleaved_rope_triton
  -> apply_interleaved_rope_kernel
```

`apply_interleaved_rope_kernel` currently declares the runtime sequence length `S` as `tl.constexpr`. As a result, every previously unseen sequence length creates a separate Triton specialization:

```text
S=112 -> compile
S=148 -> compile
S=205 -> compile
S=311 -> compile
...
```

This is especially expensive on Ascend because a Triton cache miss invokes the Ascend compiler toolchain. In profiling of variable-length Qwen3-VL requests on Ascend 910B2C:

- A 15-second scheduler sample spent about 14.0 seconds under `apply_interleaved_rope_triton`.
- About 13.6 seconds were spent in the Triton-Ascend compilation path.
- Nine prefill host scopes accumulated about 20.3 seconds, while the associated device computing events accumulated about 0.20 seconds.

These measurements indicate that the latency spikes are dominated by host-side compilation rather than NPU execution.
