## Motivation

`moe_sum_reduce` has a vectorized bf16 path for `token_num > 256` that sums 16-element chunks per lane (`VEC = 16` in `moe_sum_reduce_warp_per_token_vec_kernel`), but the launcher gates it on `hidden_dim % 8 == 0` and sizes the grid from `hidden_dim / 8`. A bf16 input whose hidden dim is 8 mod 16 (e.g. 104, 120, 1032) therefore takes the vectorized path and its last 8 columns are never written, so the output keeps whatever the buffer held. At `hidden_dim = 8` no column is written at all. No shipped model config has such a hidden dim, so this is latent, but the kernel is reachable from the Triton fused-MoE runner for any `topk != 2` and it silently returns garbage for those shapes.

## Modifications

- `python/sglang/kernels/aot/csrc/moe/moe_sum_reduce.cu`: the gate and the chunk count now derive from one shared `BF16_VEC` constant that the kernel also uses, so the three literals cannot drift again. Rows that are 8 mod 16 fall through to the scalar warp-per-token path, which writes every column. Also drops a redeclared `stream` inside the fast path that shadowed the one three lines above. 13 lines.
- `python/sglang/kernels/aot/tests/test_moe_sum_reduce.py`: regression
