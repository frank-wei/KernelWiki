## Motivation

`_commit_inject_layout_kernel` looks up `req_to_token` and then `full_to_swa_mapping` for **every** verify slot, and only afterwards replaces uncommitted slots (`col >= commit_len`, including graph-padding rows with `commit_len == 0`) with `-1`. The second lookup uses the first lookup's value as an address, so a stale or garbage `req_to_token` entry in a discarded slot is still dereferenced. Writing `-1` afterwards does not undo that read.

In practice this rarely goes out of bounds, because `req_to_token` is zero-initialized and stale entries are usually still valid locations. That is also why the existing parity test, whose random entries are all in range, never caught it.
