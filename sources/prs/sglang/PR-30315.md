## Consolidation note

This PR now also contains the SWA per-request ring runtime accounting and tests previously reviewed in #31040. The two pieces must land together: with only the original pool-sizing commits, the DSV4 Flash and Pro MI35x jobs hit GPU memory access faults during concurrent prefill; the runtime ring reconciliation at the combined tip prevents the allocator from issuing locations beyond the fixed per-request SWA ring.

## Motivation

The DSV4 `unified_kv` backend has a different physical KV layout than the fp8 path, but `DSV4PoolConfigurator` sized both identically. Under `unified_kv` this over-allocates memory (and can OOM), because:

- KV is stored in **bf16 over the full latent** (`attn_head_dim * 2` bytes), not the fp8(nope) + bf16(rope) + scale 584-byte cell.
- SWA and the c4/c128 compress-states are **fixed per-request rings** (`num_req_slots * ring_size`), independent of `full_token`, so they must be fixed biases rather than per-token terms.

## Modifications

All changes are gated on the same `is_unified_kv_triton()` / `_unified_kv` switch the pool itself uses, so sizing and allocation cannot drift apart. **No behavior change on the non-unified (fp8) path.
