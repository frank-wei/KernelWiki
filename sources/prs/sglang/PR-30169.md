## Motivation

The SM100 CuteDSL chunk prefill wrappers (GDN `gdn_cutedsl.py` and KDA `kda_cutedsl.py`) did eager pool state I/O around the kernels on every layer call: `ssm_states[indices].contiguous()` to gather initial states in, and `index_copy_` to scatter final states back out. That is two extra kernel launches plus an `[N, HV, V, K]` intermediate allocation each way, per linear-attn layer per prefill step (~1 MB per seq per layer at HV=32, K=V=128, at N=64 that is ~64 MB gathered + 64 MB scattered per layer). This per-call PyTorch overhead is exactly the class that previously dragged the (fast) CuteDSL kernels below Triton before the workspace reuse fix.

The rest of the stack already does this right: the Triton chunk path fuses state I/O into its h kernel (indexed `h0` load, in-place indexed `ht` store, `chunk_delta_h.py`), and the CuteDSL decode kernel reads the pool directly with per-slot indices. Prefill was the remaining gap.
