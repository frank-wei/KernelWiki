## Motivation

`Qwen3_5GatedDeltaNet.forward` only takes the fused Triton split/reshape/cat path when the head-group
ratio `num_v_heads // num_k_heads` is 1, 2 or 4. Layouts with a ratio of 8 fall back to the eager
sequence (`fix_query_key_value_ordering` -> `.contiguous()` -> `torch.cat`), which costs four separate
data-movement kernels per GDN layer. Measured on a decode CUDA graph on MI355X (TP=8, aiter backend):

| # | Kernel | Source expression | us |
|---|---|---|---:|
| 1 | `direct_copy_kernel_cuda` (elementwise) | `b.contiguous()` | 3.8 |
| 2 | `direct_copy_kernel_cuda` (elementwise) | `a.contiguous()` | 4.0 |
| 3 | `CatArrayBatchedCopy` | `torch.cat((q, k, v))` -> `mixed_qkv` | 4.8 |
| 4 | `direct_copy_kernel_cuda` (elementwise) | materialising the non-contiguous `z` for `z.reshape(...)` | 4.4 |
| | **Total** | | **17.0** |

That is 17.0 us and 4 launches of pure data movement per GatedDeltaNet layer. Summed over the
GatedDeltaNet layers of the model measured here it accounts for ~1.17 ms of every decode iteration,
and the whole-trace `cat`/`contiguous`/`reshape` bucket was the 6th-largest kernel category at 4.9%
of GPU time.
