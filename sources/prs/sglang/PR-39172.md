## Motivation

#37465 splits every sequence of a verify / draft batch into the same number of KV segments, `max(1, min(64, pow2floor(256 / (bs * kv_heads))))`, one work-group per (segment, sequence, kv head). That is the right split when all sequences have similar length, not optimal when one batch holds requests that varies heavily in length. Two things then happen:

- the layer finishes when the longest request's segments finish, so short requests' work-groups sit idle while a 248k request streams 8x longer segments;
- above 16 sequences the per-sequence segment count halves (bs 17-32 -> 8 segments; on TP4 with 2 kv heads per rank bs 9-16 -> 8, bs 17-32 -> 4), so a 248k request runs as 31k-token segments and the kernel degrades to Triton speed. Half of the decode steps of the TP2 c32 leaderboard point are at bs 17-30.

This PR picks the segment length from the batch's actual sequence lengths and hands the kernel a compact work list, so every sequence gets as many segments as its length needs while the total work-group count stays at one per CU.
