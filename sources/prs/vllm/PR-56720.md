## Purpose

`dequantize_and_gather_k_cache_triton` walks a V4.1 prefill's whole compressed prefix once per layer, and it did so on a fixed `(num_reqs, 128)` grid with a per-token loop that issued twenty-two memory operations. Two changes here: the grid follows the length being gathered, and a token is dequantized in one pass. They compose — the first raises how many dependent-load chains are in flight, the second cuts the work each chain does.

## Sizing the grid

Each worker walks its slice of the sequence one token at a time, and every step is a dependent load: block table entry, then the page it points at, then the token inside it. The loop is bound by that chain's latency rather than by bandwidth, so the grid has to hold enough chains in flight to cover it. At batch size 1 the whole grid was 128 workgroups on a 256-CU gfx950, while a V4.1 prefill gathers the entire compressed prefix once per layer: about 3.1k serial steps per worker at a 399k-token context.
