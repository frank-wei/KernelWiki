## Purpose

DeepSeek-V4.1 has been reusing DeepSeek-V4's paged `fp8_ds_mla` record. FlashMLA has a V4.1-specific one that quantizes the RoPE dims too; this switches DeepSeek-V4.1 onto it on SM100.

| | V4 (`ModelType::V4`) | **V4.1 (`ModelType::V41`)** |
|---|---|---|
| data row | 448 B fp8 e4m3 NoPE + 128 B bf16 RoPE | **512 B fp8 e4m3, RoPE included** |
| scale row | 7 UE8M0 of 64 dims + 1 pad byte | **16 UE8M0, one per 32 dims (MXFP8)** |
| bytes/token | 584 | **528** |
| page (TMA) stride | 576 B | **512 B** |

Both records put a page's whole data region ahead of its whole scale region, so a page is `block_size * bytes_per_token` rounded up to the TMA stride. Because `block_size` is always a multiple of 32, every V4.1 page is an exact multiple of 512 — the padding the V4 record needed disappears, on top of the 9.6% smaller record.

Gated on SM100: `ModelType::V41` is absent from FlashMLA's SM90 sparse-decode feature set, so SM90, ROCm and the FlashInfer SM120 path keep the V4 record. No new cache dtype and no new flag — `--kv-cache-dtype fp8` resolves to `fp8_ds_mla` as before and the record follows the arch, exactly as `fp8_ds_mla` already means 656 B for V3.2 and 584 B for V4
<!-- upstream-excerpt-end -->
