## Overview

The SM121 `(10240, 320)` skinny-GEMM plan for the Qwen4Exp HC up projection never runs. The fused HC down projection returns its LoRA activations as a column slice, and the Qwen4Exp dispatch only accepts packed row-major inputs, so every HC up call falls back to cuBLAS. This PR lets the CuTe DSL skinny GEMM take row-major column slices, which its kernel already supports.

## Claims

- On Qwen3.8-Flash-Next NVFP4 on DGX Spark, the HC up projection is the only BF16 GEMM still on cuBLAS during decode: about 101 calls per decode step at 31.6 us each, **3.2 ms per step** (torch profiler on a main-based build, 446 MTP decode steps, c=1). With this PR those calls use the planned skinny kernel. The GEMM is bandwidth bound (6.5 MB of weight per call), so the expected saving is the per-call delta, about 0.8 ms per step (~1%), not the full 3.2 ms.
- Kernel on the real producer layout (column slice of the 336-wide down+inject output): **1.17x to 1.23x** faster than cuBLAS at M=1 to 8, bit-exact against the same kernel on a packed copy.
- No behavior change for packed inputs or other callers (Kimi-K3 and GLM-5.2 keep their own guards).
