## Motivation

Three in-tree models build their MoE router with fp32 weights: MiniMax-M3, MiniMax-M2 and HunYuan-V3. On ROCm none of the specialized `GateLinear` tiers accept an fp32 weight, so the router falls back to `F.linear`. That fallback casts the bf16 activations up to fp32 in a separate kernel, then runs the matmul on the fp32 MFMA pipe, which on gfx950 is roughly 16x slower than the bf16 one.

MiniMax-M3 has 57 MoE layers, so every forward pass pays for this 57 times.

Everything below was measured on `amd/MiniMax-M3-MXFP4` on 4x MI350X. MiniMax-M2 and HunYuan-V3 take the same code path but were not benchmarked.

## Proposed Fix

At load time the fp32 router weight is split into three bf16 terms that add back to it exactly, since three bf16 mantissas carry the same 24 bits fp32 does.

The terms are stacked into one `(3E, K)` weight, so the router becomes a single bf16 matmul writing fp32 output, plus a small kernel that sums the three result blocks. Activations stay in bf16 and the matmul runs on the fast bf16 pipe.

Sigmoid, bias add and top-k are unchanged. Below 2048 tokens the fp32 path is faster and this tier declines.

Scoped to gfx950 for now.

## Tests

4x MI350X
