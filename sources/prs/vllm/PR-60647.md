## Purpose

Fixes #60109. This is an alternative to #60117 and #60123.

HiSparse stored GPU residency by editing core block-table rows after sending them: it adopted GPU copies of host prefix pages, and nulled pages the pool reused. The edits reached the worker through `SchedulerOutput.block_table_updates`, and #60109 was a new request's row arriving twice in one step. With this PR, HiSparse owns residency, and the worker only ever sees core rows grow (the scheduler fills an imported prefix's null tail entry before the row is first sent):

- **Scheduler:** `HiSparseResidentManager` records adopted and lost pages as per-request `residency_changes`. For each scheduled request, the coordinator sends the block ids of only the pages the worker lacks (new pages, plus pages adopted or lost since the last send; a new or re-admitted request gets its full row once), in HiSparse's connector metadata. At batch scale some request gains a page nearly every decode step.
