## Overview

`invoke_moe_batched_triton_kernel` (the `BATCHED_TRITON` FP8 MoE used with DeepEP low-latency and other batched-activation all2all backends when DeepGEMM is unavailable or disabled) takes `BLOCK_SIZE_K` straight from the tuned config. With block-quantized FP8 weights the kernel loads one weight and activation scale per `BLOCK_K` tile (`offs_ks = k * BLOCK_K // group_k`), so a `BLOCK_SIZE_K` wider than the 128-wide quantization block applies one block's scale to the next block's values. 53 of the 64 shipped `fp8_w8a8, block_shape=[128,128]` configs pick `BLOCK_SIZE_K` = 256 for some batch sizes. The standard path already clamps (`fused_moe.py:843-844`); this PR applies the same clamp in the batched launcher.

No existing issue or PR covers this (searched `fused_batched_moe BLOCK_SIZE_K`, `BLOCK_SIZE_K batched fp8`, `batched triton block_shape BLOCK_K`). Rechecked 2026-10-08: open PR #51605 resizes batched Triton MoE tiles on XPU and edits the same launcher, but it does not clamp `BLOCK_SIZE_K` for block-quantized FP8 on CUDA; whichever lands second needs a small rebase.
