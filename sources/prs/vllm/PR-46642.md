## Justification

Block-quantized FP8 fused MoE was locked to `BLOCK_SIZE_N = block_shape[0]` (128) at every batch size — in both the runtime heuristic (`get_default_config`) and the tuner search space. At decode the gate-up GEMM is SM-bound: a 128-wide N tile produces too few thread blocks to fill the GPU.

This was never a kernel requirement. The Triton kernel indexes block scales per N element (`offs_bn // group_n`), so a narrower N tile that divides the quant block is valid and exposes more thread blocks. With the **swap-AB** kernel (#36559, now in main) a 64-wide N tile stays efficient on Hopper down to the smallest batches, so `BLOCK_SIZE_N=64` is the right choice across the whole low-batch range.

Changes:
- **`get_default_config`**: use `BLOCK_SIZE_N=64` (`num_stages=4`) for fp8 block-quant on CUDA up to M=8. ROCm and larger batches unchanged.
- **`benchmark_moe.py` tuner**: relax the block-quant prune filter so `BLOCK_SIZE_N`/`BLOCK_SIZE_K` that *divide* the quant block (e.g. 64 with `block_n=128`) are no longer excluded — they were silently dropped from the search space, so no prior tune could find them.
- **Configs**: retune low-batch keys of affected H100/H200 block-FP8
