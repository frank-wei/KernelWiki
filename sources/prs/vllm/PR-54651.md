### Split-row Triton top-p pipeline — dispatch and GB200 results

#### Which cases use the new split-row pipeline

Dispatch in `apply_top_k_top_p_triton` (with the `batch >= 8` gate removed, all CUDA batches reach this):

| Condition | Path |
|---|---|
| batch > 64, or p is None, or CPU/XPU | monolithic kernel (unchanged) |
| batch ≤ 64, pure top-p batch (k is None) | **split pipeline only**; per row, only rows with p < 1.0 are processed |
| batch ≤ 64, k present (mixed/top-k batches) | monolithic kernel with `STANDALONE_TOPP=False` handles rows with k < vocab (top-k-only and top-k+top-p rows, the latter including its fast top-p-after-top-k path); **split pipeline** handles only rows with k = vocab & p < 1.0 ("p-only" rows); rows with neither are untouched by both |

Per-row rule inside the pipeline: a row is processed iff `p < 1.0` and (`k` is None or `k ≥ vocab`). Note ROCm's torch `device.type` is `"cuda"`, so MI350X/MI355X also take the split path (verified there).

Scope reminder: on CUDA the default sampler is FlashInfer; this Triton path is reached when FlashInfer is disabled/unsupported, or for per-request generators, fp64-gumbel, or processed-logprobs modes.
