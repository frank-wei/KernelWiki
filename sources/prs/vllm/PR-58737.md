> [!IMPORTANT]
> **Scope: this is a kernel-level microbenchmark, not an end-to-end throughput claim.**
> The numbers below are measured on the isolated kernel, both versions in the same process. Against a multi-millisecond decode step a
> change of this size sits inside run-to-run variation (~1% on a conc=1 arm), so
> **no measurable serving throughput improvement is claimed, and none should be
> inferred.** The value is removing six of seven kernel launches on a path that is
> on the critical path at low concurrency.

## Purpose

`mamba_get_block_table_tensor`'s `"align"` branch takes the last `1 + num_speculative_blocks` block-table entries of each request:

```python
start_indices = (seq_lens - 1) // kv_cache_spec.block_size
start_indices.clamp_(min=0)
offsets = torch.arange(1 + kv_cache_spec.num_speculative_blocks, ...)
indices_to_gather = (start_indices.unsqueeze(1) + offsets).to(torch.int64)
return torch.gather(block_table, 1, indices_to_gather)
```

The arithmetic is trivial, but as PyTorch ops it is **seven kernel launches** over a `(num_reqs,)` tensor — which holds a **single element** in a one-request decode. Almost all of the cost is launch overhead rather than work.
