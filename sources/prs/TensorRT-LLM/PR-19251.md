## Upstream PR description (verbatim excerpt)

<!-- upstream-excerpt-start -->
Split out of #19183 at @BowenFu's request.

## What

`run_fp4_block_scale_moe_runner` pads its permute buffers for every **global** expert, but the expert-parallel GEMMs below only materialize rows for the experts this rank owns — every GEMM weight is checked against `local_num_experts`. Padding for the global count over-allocates by up to the EP size, which can exhaust memory on large-token prefill shapes.

Passes `local_num_experts` to `getMaxPermutedPaddedCount` and `getMaxNumCtasInBatchDim`.

## Why it is its own PR

This is the FP4 block-scale path **shipping today on Blackwell**, so it shrinks a live allocation for every existing EP deployment. If the bound is ever short the failure mode is an out-of-bounds permute write rather than a clean error. It was originally carried in #19183 (Rubin SM107 enablement), where nothing exercises it — so it is split out to get a real build, an EP-sized run, and routing-kernel owner review on its own merits.

## Status / what reviewers should demand

- [x] Needs an EP-sized run (EP > 1) to confirm the tighter bound holds for the permute write.
- [x] Routing-kernel owner review on whether `getMaxPermutedPaddedCount` / `getMaxNumCtasInBatchDim
