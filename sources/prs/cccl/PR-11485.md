## Upstream PR description (verbatim excerpt)

<!-- upstream-excerpt-start -->
`DeviceRunLengthEncode::Encode` fails with an illegal memory access for key types larger than 16 bytes. Those keys cannot take the lookahead path, so they go through `reduce_by_key::dispatch_streaming`, and a key that large also makes the agent's temporary storage exceed the shared memory limit, so `vsmem_helper_default_fallback_policy_t` moves it to global memory. The streaming dispatch passes `vsmem_t{nullptr}` for that memory and reads the block size off the unwrapped policy, so the kernel writes through the null pointer. Reproduced with a 512-byte key and 5000 items; compute-sanitizer reports invalid global writes at `nullptr + blockIdx * vsmem_per_block`.

This queries the fallback-aware block size, items per thread and vsmem size through `determine_threads_items_vsmem`, allocates `max_num_tiles * vsmem_per_block` and passes it at both launch sites, which is what `DispatchReduceByKey` already does. Partitions are launched in order on one stream, so one partition's worth is enough.

The new test mirrors `catch2_test_device_reduce_by_key_vsmem.cu`; equivalents exist for reduce_by_key, merge_sort and select_if but not for RLE encode, which is why this was not caught.
