## 📌 Description

On SM107, `add_rmsnorm_fp4quant` (CuTe-DSL) does not get the measured SM100/SM103 config. It falls back to the generic launch heuristic in `_compute_launch_config`. This PR adds an SM107 branch, `_compute_sm107_launch_config`, next to the SM100/SM103 one.

**Why.** Every thread stages `num_vec_blocks` 16-byte vectors of each of input, residual and weight with `cp.async` before the first `cp_async_wait_group`. For H >= 1024 the generic heuristic gives 4-8 vectors per tensor, so each thread has 12-24 copies in flight. On SM107 that config keeps the kernel far below memory bandwidth at every M measured. It is slower than the same kernel on SM103 and slower than the unfused path.

**What.** Cap staging at two vectors per tensor:
- Widen `threads_per_row` to `ceil(H / (2 * vec_size))`, rounded up to a whole warp and capped at 1024.
- Use one row per CTA when `threads_per_row` >= 128. Smaller rows still pack to 128 threads per CTA.
- When the generic config already has <= 2 vectors per thread (H <= 512), keep it unchanged.
