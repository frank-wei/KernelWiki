## Summary

The generated MegaMoE v3 family (`csrc/experimental/mega_moe_v3`, `flashinfer/experimental/mega_moe_v3`) shipped every schedule twice, once per architecture, although the kernels differ only in the SM count. This folds the family into **one program per schedule**:

* **Kernels.** The pipeline schedules carried the SM count as `#define NUM_CTAS 148|152` plus three literals derived from it (the scheduler wave count and the combine token-chunk walk). `NUM_CTAS` is now a compile-line definition (`#ifndef NUM_CTAS` / `#error`), supplied by the loader from the route's per-architecture SM count, and the derived literals are `NUM_CTAS` expressions. The grouped kernels never carried an SM count and were byte-identical across architectures. The FP4 16- and 128-token pipeline schedules select different producer instructions per architecture and stay as per-architecture pairs (`..._sm100a` / `..._sm103a`).
* **Bindings.** One thin `tvm_ffi_utils.h` launcher per schedule (`tvm::ffi::CUDADeviceGuard`, the shared `check_*` helpers, a function-local static dynamic-smem opt-in). The previous files each carried a private device guard, an SM-count cache, private check helpers and a mutex-
<!-- upstream-excerpt-end -->
