## Summary

The Kimi-K3 LatentMoE front / tail backend (`flashinfer.experimental.kimi_k3_latent_moe`) planned every route for a
fixed 148-SM device and refused other parts. It now derives every plan from the device's `multi_processor_count`
and admits a device when its SM count is in the qualified set `{148, 152}` and every kernel key of the resolved
route is registered; other counts raise `NotImplementedError` naming the device and its count.
`generated_program_available(arch, stage, tp, tokens, num_partials=1)` accounts for the partial count.

No kernel source changes: the same generated programs serve both SM counts (plans differing only in runtime
parameters reuse the registered program). The 148-SM plans are unchanged.

## Tested configurations

| device | arch | SMs | status |
|---|---|---|---|
| NVIDIA B200 | sm_100a | 148 | qualified: 148-SM plans unchanged bit-for-bit; 63 / 64 export rows pass after the retry round — the front T=16384 row (a 2-ms prefill GEMM that runs at the part's power cap) fails only the protocol's loaded-SM-clock validity gate (1567 / 1965 MHz < 0.85 with two measuring workers, 1627 with four); the tail T=16384 and tail T=1024 rows passed on the retry
