## 📌 Description

Fixes #6399. `topk_clusters_exact` (what `top_k(..., deterministic=False)` uses on SM100/SM103) sometimes returns a wrong top-k when a row is split across more than one cluster.

The race: at the start of each round, thread 0 resets `shared_num_cached_count[phase]`. The previous round read that same slot (as `[phase ^ 1]`) after its last `__syncthreads`, and only the cluster arrive/wait sits in between. Arrive comes before the read, so a slow warp can read 0 and drop its candidates. This adds a `__syncthreads()` at the top of the round loop.

Measured on B300, fp32 `randn * 3` `[rows, 248320]`, k=20, `deterministic=False`, 500 calls per row:

| rows (clusters per row) | before: wrong / garbage ids | after | kernel time before → after |
|---|---|---|---|
| 160 (2) | 3 / 0 | 0 / 0 | 94.5 → 95.0 µs |
| 200 (2) | 18 / 7 | 0 / 0 | 96.6 → 97.2 µs |
| 240 (2) | 26 / 4 | 0 / 0 | 117.5 → 118.2 µs |
| 252 (2) | 14 / 8 | 0 / 0 | 120.2 → 120.9 µs |
| 255 (2) | 17 / 3 | 0 / 0 | 121.1 → 121.2 µs |
| 252 (4, forced) | 23 / 10 | 0 / 0 | 127.3 → 128.5 µs |
| 64 (4), 512 (1), 252 with k=2048 | 0 / 0 | 0 / 0 | within ±1 µs |
