## Summary

- preserve the existing `128x64` flash-decoding MHA tile as the first choice and unchanged CUDA path
- inspect generated HIP LDS and VGPR usage before launch
- fall back to the existing correct `64x64` tile only when the larger tile exceeds the current AMD device's resource budget
- add a gfx942 runtime regression against the PyTorch reference

## Why

`examples/flash_decoding/example_mha_inference.py` currently hardcodes `BLOCK_M=128`, `BLOCK_N=64`. On gfx942 the generated split kernel requires 66,048 bytes of dynamic LDS against a 65,536-byte device limit and reaches the 256-VGPR ceiling, so `hipModuleLaunchKernel` fails with `invalid argument`.

A device-name conditional would unnecessarily freeze smaller tiles onto future AMD GPUs. Instead, this change compiles candidates in descending order and accepts the first whose generated module fits `get_arch(target).smem_cap` and the available register-file budget. CUDA returns the original `128x64` candidate without entering the HIP resource-selection path.
